# Access Policy — единая модель доступа Meridian

Живой документ. Обновляется по мере решения открытых вопросов матрицы
доступа. Источник: архитектурный ревью от 2026-08 (полный текст — в истории
чата/коммитов), см. коммиты `357b9bd`..`1a3b23f`.

## Статус: решено

### VIEW
`get_entity_for_view(db, model, entity_id, user_id, *, hide_as_404=False)` — lab_access.py

Владелец, ИЛИ участник лабы (любая роль), ИЛИ кто угодно если `visibility == "public"`.
`user_id=None` (гость) — только public-ветка.

По умолчанию отказ в доступе — `403` (палит факт существования сущности, но
не даёт к ней доступ; так везде в проекте). `hide_as_404=True` превращает тот
же отказ в `404` — для фич, которые намеренно не хотят подтверждать даже факт
существования (сейчас единственный потребитель — `comments.py`, обсуждения:
посторонний не должен узнавать, что у чужой приватной записи вообще есть
тред). Один и тот же код проверки, разница только в статусе ответа —
осознанное решение сессии (не заводить две отдельные функции ради одной
строчки).

Списки используют эквивалентное SQL-условие `entity_visibility_filter()`,
у которого те же keyword-параметры `requested`/`lab_id` — см. ATTACH ниже.

### LINK
`can_link(db, model, entity_id, user_id)` — lab_access.py

Создание любой связи на чужую сущность (EntityHypothesis, Prediction.hypothesis_id,
graph Link) требует, чтобы инициатор **видел** целевую сущность —
`can_link` = `get_entity_for_view` с отдельным именем под будущее развитие.

Правило: **линк = осознанная публикация связи**, не приватный внутренний
указатель. Нельзя привязать чужую непубличную сущность вслепую по id.

Применяется в: `add_task_hyp`, `add_question_hyp`, `create_pred`, `update_pred`
(при смене hypothesis_id), `graph.add_link`.

LINK для постороннего (не участника лабы) на **публичную** сущность лабы —
уже разрешено сегодня, отдельного решения не требовалось: ветка
`visibility == "public"` в `get_entity_for_view` не завязана на членство.

### LAB MANAGE (было названо EDIT — переименовано, см. коммит `b24507d`)
`get_entity_for_lab_manage(db, model, entity_id, user_id)` — lab_access.py

Владелец сущности ИЛИ владелец/админ лабы — но **только организационные
операции**: привязка/отвязка гипотез, управление шкалами, expectations.

**НЕ даёт права редактировать содержимое** сущности (текст, поля) — это
осознанное ограничение, не баг. Все `update_*` эндпоинты (hypotheses/
observations/questions/worldview) строго owner-only, и это правильно.

Обоснование: контент неприкосновенен для автора, даже для lab admin/owner.
Лаборатория — контур организации исследования, не право переписывать чужой
контент. Критично для федерации (см. ниже) — внешний инстанс не сможет
разрешить своему admin редактировать содержимое чужой записи.

### Предложенные гипотезы лабы (ATTACH/REJECT) — исключение из LAB MANAGE

`POST /labs/{lab_id}/hypotheses/{hid}/attach`, `POST /labs/{lab_id}/hypotheses/{hid}/reject`
— labs.py

Механизм: участник лабы создаёт гипотезу с `lab_id = эта лаба` (обычный
create-эндпоинт, `resolve_lab_attachment`), но не привязывает её к цели
лабы — это "предложение". Такая гипотеза уже видна всем участникам лабы
через `entity_visibility_filter` (ветка `lab_id.in_(member_lab_ids)`
не зависит от `visibility`), но не входит в счётчик "N гипотез" (см. ниже)
и не показывается как конкурирующая, пока не прикреплена.

**Автопривязка при создании — только для owner/admin** (`create_hyp`): они вправе привязывать, поэтому
их гипотеза с `lab_id` сразу становится конкурирующей. Гипотеза обычного участника остаётся предложением,
пока owner/admin не примет её (`attach`). Тесты: `tests/test_lab_hypothesis_proposals.py` (в том числе: участник не может привязать предложение к цели напрямую через `/tasks/{goal}/hypotheses/{hid}` — там требуется право управления лабой, как и в `/questions/{id}/hypotheses/{hid}`; для вопросов проверка по коду, отдельного теста пока нет).

Owner/admin лабы видит очередь предложений (`Hypothesis.lab_id == lab_id`,
не привязанные к цели через `EntityHypothesis`) и может:
- **attach** — создать `EntityHypothesis` (гипотеза становится конкурирующей
  по цели, попадает в общий счётчик и в LabHypothesesRail). Это НЕ мутация
  гипотезы — создание отдельной связующей записи, ровно как LINK.
- **reject** — снять `lab_id` (→ `None`) и вернуть `visibility` к `"private"`.

**REJECT — осознанное, узкое исключение из правила "LAB MANAGE не даёт
права редактировать содержимое"** (см. выше): единственное затрагиваемое
поле — `lab_id`, поле организационной принадлежности лабе, не контент
гипотезы. Все содержательные поля (`name`, `description`,
`falsification_criteria`, `status` и т.д.) по-прежнему редактируются
только автором через `update_hyp` (owner-only, без изменений). Обоснование:
`lab_id` уже был проставлен ДЕЙСТВИЕМ САМОГО автора при создании как акт
"предложить лабе" — reject admin'ом лабы является симметричным ответом на
это конкретное действие (аналог "отклонить заявку"), не произвольным
редактированием чужой записи. Для будущей федерации это по-прежнему
безопасно: `lab_id` — локальное поле принадлежности инстансу, не часть
портируемого контента записи.

Счётчик "N гипотез" в `GET /labs/{lab_id}` считает только конкурирующие
(через `EntityHypothesis` к цели), не предложенные — иначе число расходится
с тем, что видит пользователь в сайдбаре.

Счётчик "N результатов" в `GET /labs/{lab_id}` считает сущности `Result` (НЕ закрытые
прогнозы — раньше было так, и бейдж расходился со вкладкой) тем же запросом видимости
`visible_results_stmt` (lab_access.py), что и список `GET /results`, и для текущего
зрителя: участник видит все результаты лабы, остальные — только опубликованные в
публичной лабе. Копировать фильтр видимости в другое место нельзя — только вызывать функцию.

### CONTRIBUTE — операции не существует (осознанно)
Была функция `get_entity_for_contribute` — удалена (коммит `1a3b23f`) как
мёртвый код, никогда не вызывавшаяся ни в одном роутере.

"Добавить вклад в чужую сущность" уже реализуется без отдельной операции:
своя сущность (task/prediction/observation) + `can_link` к чужой гипотезе.
Не мутация чужих данных — создание своей + ссылка.

Если позже понадобится настоящее совместное редактирование одной записи
(не через линк, а прямая правка несколькими людьми) — это **отдельная,
осознанно спроектированная задача** (версионирование, история правок), не
донастройка старого кода.

### ATTACH (lab_id при создании сущности)
`resolve_lab_attachment(db, lab_id, requested_visibility, user_id)` — lab_access.py

Единая точка входа: без `lab_id` — пользователь свободно выбирает
visibility. С `lab_id` — лаба должна существовать, пользователь обязан быть
участником, видимость выводится из `lab.is_public` через `visibility_from_lab()`
(`requested_visibility` игнорируется). См. документ-ревью, п.5/п.6 — устранено
расхождение "visibility задаёт пользователь" vs "visibility выводится из lab".

Этот же баг (lab_id/visibility без проверки членства) отдельно и независимо
воспроизвёлся в `predictions.py`, `tasks.py` (инлайн-копии вместо вызова
`resolve_lab_attachment`) — найдено и исправлено в сессии по итогам аудита
"Лаборатории", `questions.py`/`worldview.py` содержали ту же дыру, исправлены
параллельно. Коммит `f8f0727` + регрессионные тесты в
`tests/test_lab_attach_membership.py`. Вывод: любая независимая копия этой
проверки — кандидат в баг, даже если выглядит правильной на вид.

**Видимость в формах и решение владельца (11.10).** Публичная лаба даёт публичные записи — оставлено осознанно. Формы во вкладках лабораторий поэтому не предлагают выбор видимости, а показывают, что получится (`LabLockedNote`, фронт `lib/lab-lock.ts`), и форсируют `lab_id` (`lockedLabId`). Реально сохранённая видимость и доступ постороннего проверяются `tests/test_lab_entity_visibility.py` (наблюдения, прогнозы, гипотезы).

### Параметризация списковых/точечных проверок (requested, lab_id)
`entity_visibility_filter(model, user_id, *, requested: set[str] | None = None,
lab_id: int | None = None)` — те же kwargs, что и раньше жили отдельной
копией в `users.py::_visibility_filter` (для `/users/{username}/stats`):
`requested` сужает набор допустимых уровней `visibility`, `lab_id` сужает
lab-ветку до конкретной лабы, не трогая private/public строки. Базовое
условие (own/public/lab-членство) было тождественно уже существовавшему —
`users.py` теперь просто делегирует сюда, вместо повторной реализации.

### Запись, открытая через связь (opened_via_link_condition, record_shares)
Приватная запись N, связанная с лабораторной записью R (visibility = "lab"), может быть открыта участникам этой
лаборатории только для чтения. Правила:
- Решает владелец N, явно: при создании связи (и при операциях, которые её создают: прогноз с гипотезой, привязка
  гипотезы к задаче или вопросу, откат удаления связи, в том числе пакетный) сервер отвечает 409 `needs_consent`
  с вариантами `options`, клиент повторяет запрос с `?share=me|lab|public`.
- `me`: связь есть, запись остаётся приватной. `lab`: строка в `record_shares`, участники читают N через связь
  (только в закрытой лаборатории). `public`: запись становится публичной (только для публичной лаборатории;
  закрытому прогнозу недоступно: его видимость заморожена).
- Открывает только владелец N; если открыть пытается не он, 403. Один хоп: N связана с R напрямую.
- Согласие снимается при удалении связи, привязки или записи и при смене видимости записи (возврат в private
  не воскрешает доступ).
- Согласие привязано к лаборатории и записи-источнику R, а не к её состоянию: R в private закрывает N, возврат R
  в ту же лабораторию открывает N снова (владелец соглашался именно на это), перенос R в другую лабораторию не
  открывает N ни в старой, ни в новой. Защищено `test_open_via_link_r_side.py`.
- В сигнал зрелости и счётчики лаборатории такие записи не входят (lab_id пуст); списки вкладок показывают их
  только при `include_opened=true`.
- Результаты (Result) в эту модель не входят.
`get_entity_for_view` и `can_link` остаются строгими: чтение через связь идёт отдельными функциями
(`get_entity_for_read`, `can_read_via_link`, `opened_via_link_or_never`). Не путать с `can_link`: он проверяет,
что можно привязать, а не что видно.

Старый механизм `lab_reachable_ids` (автоматический доступ участников к соседям лабораторных записей без согласия)
удалён: он нигде не вызывался. Поведение «связь с лабораторной записью = публикация» больше не действует.
Защищено тестами `test_open_via_link*.py`, `test_publication_*.py`, `test_lab_reachability.py` (Link-ветка).

(6 базовых из `ENTITY_MODELS` + `result`).

Изменено 2026-09-20: раньше чтение списка тоже было owner-only, хотя `ImagesTab`

Сами файлы отдаются публичной статикой `/api/uploads/entity_images/<имя>` БЕЗ проверки
прав: защита — только генерируемое сервером имя (`image_processing.save_processed`) и то,

Для вложений (не картинок) устроено иначе — см. следующий раздел.

### Файлы: вложения (EntityAttachment) — реализовано 2026-09-20

API: `attachments.py`. Родители — ровно 6 базовых типов (`ENTITY_MODELS`);
`result` и прочее → 404 (у Result свои правила видимости, `is_published`, —
не проверены на `get_entity_for_view`). Картинки сюда не принимаются, у них
свой пайплайн (`/images`, EntityImage).

| Операция | Кто |
|---|---|
| `POST /{type}/{id}/attachments` | только владелец сущности (`require_owned_entity`) |
| `GET /{type}/{id}/attachments`, `GET /attachments/{id}`, `GET /attachments/{id}/download` | `get_entity_for_view(hide_as_404=True)` через `get_current_user_optional`: владелец, участник лабы (lab-visibility), гость для public; остальным 404 |
| `DELETE /{type}/{id}/attachments/{aid}` | только автор вложения, мягкое (`deleted_at`) |

Список отдаёт только метаданные (`has_text_content`), текст — в `GET /attachments/{id}`.

**Хранение и раздача.** Файлы — в `ATTACHMENTS_DIR` (`backend/attachments/`, том
в compose), НЕ в `uploads/` (тот раздаётся публичной статикой без проверки
прав). Имя на диске — `uuid.ext`, генерирует сервер; оригинальное имя — только
в БД и только для показа. Скачивание — исключительно через `/download`:
`Content-Disposition: attachment`, `nosniff`, `CSP: sandbox`, `no-store`.

**Классификация** (`attachment_storage.py`): по расширению из закрытого белого
списка + содержимому (PDF-сигнатура, структура zip для docx/xlsx, валидный
UTF-8 без NUL для текста). `Content-Type` клиента игнорируется. HTML/SVG/XML,
исполняемые и неизвестное отклоняются. Лимиты: файл ≤ 10 МБ; `text_content` в
БД — только текст ≤ 256 КБ (больше — файл принимается, но без инлайн-текста);
≤ 10 файлов за запрос.

**Важно для фронта:** nginx (`client_max_body_size 20M`) ограничивает ЗАПРОС
целиком, а не файл — файлы слать по одному, иначе 5×10 МБ получат 413 до
приложения.

**Event-log:** вложения логируются в `events` (`EVENT_LOGGED_MODELS`), мягкое
удаление — как `updated` с `deleted_at`; событие `created` не эмитится, в
ленту вложения не попадают.

**Фронтенд:** вкладка «Файлы» (`components/entities/files-tab.tsx`) = `ImagesTab` + `attachments-section.tsx`; идентификатор вкладки на страницах по-прежнему `images`. Загрузка — по одному файлу на запрос; просмотр текста — `GET /attachments/{id}`, подсветка `highlight.js` (языки грузятся динамически, лимит 100 000 символов, покрытие языков бэкенда проверяет `lib/attachments.test.ts`). Тексты — через `useT` (`attachmentsTab.*`, `filesTab.*`).

**Не реализовано (осознанно):** физическая чистка файлов (GC), fork/branch
родителя с вложениями, AI-описание code/document, каскад при удалении родителя
(строки и файлы остаются, но недоступны — родитель не проходит проверку
доступа), кодировки текста кроме UTF-8.

лабе). Добавленный `test_lab_access_matrix_result.py` закрывает только то,
чего там не было: базовое чтение владельцем/участником/админом внутри
приватной лабы, и ролевой creation-gate в public-open/public-approval
(включая join-request флоу) — то есть тот же класс проверок, что у
остальных 6 типов, без дублирования уже существующего покрытия.

### Снимки лабы (checkpoints) — реализовано 2026-10-04

Подробности — `LAB_CHECKPOINTS.md`. Права: создаёт любой участник; публикует (`is_published`) только owner/admin
и только в публичной лабе; не участник закрытой лабы получает 404; не участник публичной видит ТОЛЬКО
опубликованные снимки и только по белому списку полей (`services/checkpoint_redaction.py`) — без
комментариев, файлов, корзины и людей. Файлы снимка отдаются только участникам.

**Люди и удаление в снимках (решение 06.10.2026).**
- Снимок создаёт любой участник лабы: роли owner, admin, member (роли «только чтение» нет).
- В снимок копируются комментарии и посты ленты вместе с `author_id`, состав участников лабы с ролями, `user_id` у записей.
  Удаление комментария автором (`comments.py`, физическое) и удаление аккаунта (`CASCADE`) на уже сделанные снимки
  НЕ влияют: копия остаётся и читается участниками лабы. Анонимизировать её задним числом нельзя без поломки хешей.
  Это сознательное исключение из «удалённое пропадает» ради «нотариальной» ценности. Предупреждение об этом есть при
  удалении лабы; при удалении комментария и аккаунта его нет (не проверялось, открытый пункт интерфейса).
- Снимок видят ВСЕ текущие участники лабы, в том числе вступившие после его создания: старые снимки открывают им
  комментарии и состав лабы «как было». Постороннему комментарии, файлы, люди и корзина не отдаются никогда.
- Если понадобится убрать чьи-то слова из снимка (запрос на удаление данных), нужен механизм «редакции» формата v2:
  заменить содержимое элемента меткой, сохранив его `item_hash`, чтобы хеш дерева остался проверяемым. Пока его нет,
  править `snapshot_data` вручную нельзя: это ломает проверку.

## Статус: открыто / не начато

### Транзакционные границы (документ-ревью, п.11)
`_set_tags()` и подобные хелперы коммитят транзакцию внутри себя, до того
как основная операция (embedding, AI-классификация) завершена. Риск
частично сохранённых операций при падении на поздних стадиях. Требует
отдельного захода: поднять транзакционную границу на уровень роутера,
единый commit в конце. Не начато.

### Background jobs (документ-ревью, п.12)
FastAPI BackgroundTasks — не production queue, задача теряется при
рестарте процесса. Нужен переход на Redis/queue + worker при росте
нагрузки. Не начато, не приоритет пока пользователей мало.

## Принципы для будущей федерации лабораторий

Зафиксировано явно в этой сессии — Алексей планирует децентрализованную сеть
исследовательских репозиториев (сначала в рамках одного Meridian, потом —
локальные инстансы с подключением). Это должно быть учтено в любом новом
access-решении уже сейчас:

1. **Каждый инстанс пишет только свои сущности.** Линк — это ссылка, не
   мутация чужих данных. Уже так устроено (LINK, отказ от CONTRIBUTE).
2. **Не вводить операции, требующие мутации чужой сущности** (совместное
   редактирование одной записи) без явного проектирования — это
   distributed write conflict в будущей федерации, дорого решается
   (CRDT/merge/блокировки между инстансами).
3. **Вся access-логика — за именованными функциями** (`can_link`,
   `get_entity_for_view`, `get_entity_for_lab_manage`,
   `resolve_lab_attachment`, `entity_visibility_filter`), не инлайн SQL по
   роутерам. Когда дойдёт до федерации, менять придётся эти несколько
   функций, а не десятки эндпоинтов.
4. Что именно будет "видимостью" между инстансами (push/pull, чья БД
   авторитетна, разрешение конфликтов видимости) — не спроектировано,
   осознанно отложено до появления фактов о том, как федерация будет
   выглядеть технически.

### Файлы записей лаборатории (06.10.2026)
`GET /labs/{id}/files` — только участники (остальным 404). Показывает вложения и картинки живых записей этой лаборатории
с привязкой к записи; записи из корзины и удалённые вложения не показываются, личные записи и записи других лабораторий —
тоже. Потолок ответа — `MAX_LAB_FILES` (500), у ответа есть `count` и `truncated`. Действия с файлами (просмотр кода, замена,
версии, загрузка) — на странице самой записи, права там прежние.

**Файлы и снимки (07.10.2026).** Байты вложений и картинок живых записей копируются в снимки лаборатории и остаются там навсегда:
удалить файл из снимка после его создания нельзя. Сознательное следствие «нотариальной» неизменяемости; пользователю об этом
сказано во вкладке «Файлы» лаборатории. Механизм «редакции» (снятие содержимого с сохранением хеша) — задача формата v2.

Файлов у самой лаборатории (не привязанных к записи) нет сознательно (решение 07.10.2026): вкладка «Файлы» — обзор файлов записей.
Цель лаборатории (задача или вопрос) — обычная запись лаборатории с `lab_id`, её файлы показываются там же. Если появится
запрос на лабораторные файлы, первый кандидат — файлы к результатам (у `Result` уже есть `lab_id`, права и публикация).

**Удаление лаборатории.** Вместе с ней удаляются следы без FK: стадия лаборатории, переводы её названия/описания и переводы
сообщений её заявок (`tests/test_lab_delete_cleanup.py`).

### Режимы графа «а что, если» и «слепые зоны» (13.10.2026)

Эндпоинты (все требуют входа): `POST /graph/what-if`, `POST /graph/lab/{id}/what-if`, `POST /graph/global/what-if`,
`GET /graph/blind-spots`, `GET /graph/lab/{id}/blind-spots`, `GET /graph/global/blind-spots`.
Чистая логика: `services/hypothesis_evidence.py` (`what_if`, `what_if_delta`, `load_bearing`) и `services/blind_spots.py`.

Правило видимости, которое нельзя ослаблять: уровень зрелости и абсолютный сигнал гипотезы включают `evidence_signal`
(вклад закрытых прогнозов автора) и его приватные наблюдения. Поэтому:
- **Владелец гипотезы** получает полный расчёт (уровни до/после, вердикт, несущие наблюдения).
- **Все остальные** (участники лаборатории, глобальный граф) получают только сдвиг сигнала от видимых им наблюдений
  (`verdict="unknown"`, без уровней и абсолютного сигнала). В лаборатории видимыми считаются наблюдения с `lab_id`
  этой лабы, в глобальном графе только `visibility="public"`.
- В лабораторном режиме считаются только гипотезы с `lab_id` этой лабы (гипотезы, попавшие в граф через цель, пропускаются).
- Слепые зоны: связь считается, только если оба её конца в видимом наборе, поэтому для лаборатории и глобального графа
  «нет прогнозов» и «наблюдение без связей» могут быть завышены. Это сказано в интерфейсе.
- Прогнозы в «что если» не пересчитываются: их вклад влит в `evidence_signal` и отдельно не хранится.

Тесты на утечки: `test_what_if_lab_api.py`, `test_what_if_global_api.py`, `test_blind_spots.py`.

### Заголовок наблюдения обязателен (13.10.2026)

`title` не бывает пустым: схема (`NonEmpty255`), текст не бывает пустым HTML (`RichRequired`, `core/plain_text.py`),
репост подставляет заголовок из текста, в БД стоит `CHECK observations_title_not_blank` (миграции `c395dfefc8d0`, `3b1d784c71ae`).
Любой новый код, создающий `Observation(...)` напрямую, обязан передавать непустой `title`.
Тесты (`tests/conftest.py`) отказываются стартовать, если БД не `postgres-test/*_test`: `_clean_db` делает TRUNCATE всех таблиц.

## Лента карточками (GET /feed/groups/*)

- Лента строится из САМИХ записей, а не из копии видимости в events: видимость, корзина и лаборатория читаются у записи
  в момент запроса (события дают только время последней активности). Утечка «запись скрыли, а событие осталось» невозможна.
- Связи склеивают записи в карточку только между записями, видимыми в этой ленте: приватная запись не соединяет чужие
  карточки и не выдаёт своё название.
- Лента лаборатории: участнику видны записи lab и public этой лаборатории, не-участнику публичной лаборатории — только public
  (публичная лаборатория не делает записи публичными).
- Карточка одной записи (GET /feed/groups/entity/{type}/{id}): у публичной записи — публичные соседи, у лабораторной —
  публичные и лабораторные той же лаборатории; личной записи карточки нет (404).
- Теги публичной записи публичны вместе с ней.
- Счётчиков связей (за/против/связано, общее число) в ответе нет: они считали все связи владельца, в том числе
  приватные, и гость видел бы их число (охраняют `test_feed_hidden_link_counts`, `test_recently_confirmed_feed`).

## Личные заметки владельца на публичной и лабораторной записи

Правило одно, оно живёт в `app/core/personal_notes.py`: **корневой комментарий владельца записи без позиции
(`stance IS NULL`) — его заметка для себя, как и любой ответ на такую заметку**. Остальное — обсуждение
(страница дискуссии всегда ставит позицию). Владелец видит всё, остальные — только обсуждение.

Где применяется (добавляя новое место чтения комментариев, подключайте то же правило, а не пишите условие заново):
- `GET /comments/{type}/{id}` — список скрывает заметки от не-владельца;
- счётчик `comment_count` в ленте и на карточке записи — заметки не считаются;
- перевод комментария (`translatable_resolvers`) — чужую заметку не отдаёт;
- `POST /comments` — под скрытой заметкой другой зритель ответить не может (400);
- снимки лаборатории (`collect_items`) — заметки в снимок не копируются: снимок видят участники.
  Следствие: снимок не содержит личных заметок владельца и не может их восстановить; снимки, созданные до этого
  правила, их содержат.

- бейдж непрочитанных (`GET /comments/unread/summary`) — чужая заметка в него попасть не может (она «от самого владельца»);
  каждая запись группы проходит `_check_entity_access`, поэтому запись, ставшая приватной или удалённая, из бейджа исчезает
  (раньше в нём оставались её название и первые 80 символов ответа).
- письмо об ответе (`_notify_comment_recipients`) — тем же правилом: получателю без доступа на чтение записи письмо не уходит
  (в нём название записи и текст ответа).

## Граф связей записи для гостя (`GET /graph/related/{type}/{id}`)

Эндпоинт принимает и гостя (uid=None). Корень проверяется тем же `get_entity_for_read` (гостю запись «открыта через
связь» не бывает — `get_entity_for_read` без пользователя эту ветку пропускает), обход идёт по тому же `_visible`, но для
гостя видимым узел бывает только публичным: ни «своих», ни лабораторных, ни открытых через связь. Приватная запись
по-прежнему не служит мостом. Управления связями (capabilities, can_edit, shared_with, effect) гость не получает.
